# Database Rules

## One Database, One Client

The bridge uses a single SQLite database, `bridge.db` (path from `DB_PATH`, default `mcp-bridge/bridge.db`), accessed only through `DbClient` (`db/client.ts`). It stores messages and tasks; conversations are derived from them (there is no conversations table).

`createDatabase()` (`db/schema.ts`) sets `journal_mode = WAL` and `foreign_keys = ON`, then applies `MIGRATIONS`. The test helper `createTestBridgeDb()` also sets `busy_timeout = 5000`.

## Prepared Statements Only

Never interpolate SQL strings. All queries use named parameters:

```typescript
// Correct
const stmt = db.prepare("SELECT * FROM messages WHERE id = @id");
stmt.get({ id });

// Wrong — SQL injection risk
db.prepare(`SELECT * FROM messages WHERE id = '${id}'`);
```

Prepared statements are created once at client construction time and reused for every call (`markAllRead` is the one method that still prepares per call). This is both a security requirement and a performance optimization.

## DbClient Interface (bridge DB)

Methods:
- `insertMessage(msg)` → `MessageRow` (id generated by the client)
- `getMessage(id)` → `MessageRow | undefined`
- `getMessagesByConversation(conversation)` → `MessageRow[]` (oldest first)
- `getUnreadMessages(recipient)` → `MessageRow[]`
- `markRead(id)` / `markAllRead(recipient)`
- `insertTask(task)` → `TaskRow` (status starts `pending`)
- `getTask(id)` → `TaskRow | undefined`
- `getTasksByConversation(conversation)` → `TaskRow[]`
- `updateTaskStatus(id, status, analysis?)`
- `getConversations(limit, offset)` → `ConversationSummary[]` / `getConversationCount()` → `number`
- `transaction<T>(fn: () => T): T` — wraps multiple operations atomically

## Transactions

Use transactions for any multi-step write sequence. The `transaction()` method is synchronous (better-sqlite3):

```typescript
const result = db.transaction(() => {
  const msg = db.insertMessage(msgInput);
  db.updateTaskStatus(taskId, "in_progress");
  return { message: msg, taskUpdated: true };
});
```

If any statement inside throws, the entire transaction is rolled back automatically.

## Bridge Schema (schema.ts)

Tables:
- **messages** — `id` (UUID), `conversation`, `sender`, `recipient`, `kind`, `payload`, `meta_prompt`, `created_at`, `read_at`
  - `kind` CHECK: `'context' | 'task' | 'status' | 'reply'`
- **tasks** — `id` (UUID), `conversation`, `domain`, `summary`, `details`, `analysis`, `assigned_to`, `status`, `created_at`, `updated_at`
  - `status` CHECK: `'pending' | 'in_progress' | 'completed' | 'failed'`

Indexes: `idx_messages_conversation`, `idx_messages_recipient (recipient, read_at)`, `idx_tasks_conversation`, `idx_tasks_status`.

All IDs are UUID strings generated by the client (`randomUUID()`). `created_at` is filled by the column default (`datetime('now')`); `read_at` and `updated_at` are written by the client as ISO 8601 strings.
